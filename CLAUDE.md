# orca

A light-context agent harness with one adaptive tool loop and focused workers. Delegation, review and publication are independent capabilities. One tmux session per project contains agent windows; persistent state and process supervision supply continuity. See docs/ADAPTIVE_RUNTIME.md for current behavior.

Bun + TypeScript. Use `bun` for everything (`bun test`, `bun run check`, `bun src/cli/main.ts`). No Node, npm or vite.

`install.sh` bootstraps the dedicated `~/.orca/.runtime/app` checkout and delegates the build/atomic binary install to `scripts/install.ts`. It preserves runtime state, refuses existing app paths, and adds PATH for supported shells unless `--no-modify-path` is passed. Bootstrap tests use temporary homes and fake downloads/builds; never run installation against the real home for validation.

Layout:

The tree has the codex-rs shape, bottom first: config → login → providers → protocol → core → exec · tui → cli. Every import points down, between packages and inside them; `src/organization.test.ts` is the check (read its header), CLAUDE.md is the prose. The orders it enforces:

- packages: `config` < `login` < `providers` < `protocol` < `core` < `exec` · `tui` < `cli` (`exec` and `tui` never import each other; type-only imports count)
- `providers/`: images · sanitize · retry < catalog/ < search/ < provider < anthropic · openai < account
- `core/`: proc · execution < data/ < definitions/ < install/ · tmux/ · prompt/ < tools/ < agent-loop/; `core/data/`: storage-lock · sqlite/ < projects/ < run-ownership/ · images/ < inbox/ < processes/ · knowledge/ · tasks/ · transcripts/ < memory/; `core/tools/`: registry < the tools (one file or sub-folder each) < mount; `core/agent-loop/`: loop/ < orc/
- `tui/`: commands/ · history · components/ < header/ · conversation/ < footer/ < screen/ < app-state < app
- files directly inside one folder are one unit (no order between them); a type a lower file needs from above is narrowed in place, e.g. `ContextDeps` in `compaction.ts` for `AgentDeps`, `ConsumeTarget` in `inbox.ts` for `Transcript`

Barrels: every folder that is imported from outside has an `index.ts` holding nothing but named re-exports of the files directly in it (`export { a, type B } from "./file"`; `export * as ns from "./file"` for a namespace; never a sub-folder, a parent, another barrel or `export *`), dependencies first. Non-test code crossing a folder boundary imports that folder's barrel (`../../core/data/tasks`), never a deep module, and adds missing names to the barrel. Two exceptions, both inside one package: imports inside a folder stay direct, and a file of an ancestor folder is imported directly too (`../sanitize`, `../../proc`, `../storage-lock`) — never the ancestor's barrel (`..`, `../..`), which would reach back into the importing folder and make a cycle; (b) still orders these. Tests (`*.test.ts`, `src/test/`) are exempt from the order and barrel rules (a)–(c) and may import anything. `core/tools/index.ts` is the barrel; `core/tools/mount.ts` is the registry mount.

Size gates (the same test): a non-test file ≤ 800 lines, a test file ≤ 1500, a function ≤ 8 parameters, a barrel ≤ 40 exports. Today's offenders are listed in the test's `DEBT` table with their current numbers as ceilings: growth fails; shrink the ceiling when the file shrinks (the test does not force it); a row within the gate must be deleted. `src/` holds only the package folders, `test/` and that test — no loose files.

- `src/tui/commands/` — what the slash commands do, separate from how the TUI shows them (`model.ts`, `accounts.ts`, `project.ts`, `settings.ts`). The project list logic is `src/core/data/projects/registry.ts`: `orderProjects`/`orderedProjects` (pinned first, each group sorted by display-name label), `togglePin`; agent liveness is `src/core/tmux/liveness.ts`: `liveAgents` (tmux windows minus the idle shell), `exitWatchdog` (the orchestrator daemon runs it on its poll; tmux errors come back as null from `liveAgentsOrNull` so they never look like "all windows gone"; see `src/core/tmux/exits.ts`), `mergeWatch` (the merged-PR watcher from `src/core/tmux/merges.ts`, run next to it in the daemon; `AppDeps.watchdog`/`AppDeps.merges` are extra per-poll watchers the TUI runs only when tests inject them), and `deleteProject` in `src/tui/commands/project.ts` (removes project state, clean managed worktrees and its pin; preserves the original checkout and local branches; refused while workers/reviewers are live/unknown or worktrees have local files; stops the orchestrator daemon and waits for its process before the tmux session dies and anything is removed, `DeleteOptions.stop`)
- `src/core/agent-loop/orc/daemon.ts` — the orchestrator as a long-lived process (`runDaemon`, the poll loop; its process entry `orchestratorAgent` is `src/exec/daemon.ts`): `orca agent --role orchestrator --project p` (what the TUI launches through `local.start`, in the `orchestrator` window of `orca-<project>`, under the same `sh -c` wrapper and `confirmLaunch` as workers) takes the project's `daemon-locks/<project>` for its lifetime (a second daemon exits 70 before writing a run record, so its launch fails and the first keeps running), runs under `supervise` (run record `runs/orchestrator.json`, crash/signal notices to its own inbox for the next daemon; a clean stop claims its run first, so no notice), and loops: answer queued requests (`clear`, `compact`, `model`, `stop`), take a cancel request for its launch (`takeCancellation`: `session.cancel()`, acknowledged under the cancel token), run the exit watchdog and merge watcher every `WATCH_MS` (2s), then `session.pending()` → `session.turn()` (status `turn`, a 100ms cancel poll meanwhile) or sleep `DAEMON_POLL_MS` (1s) — woken early by `fs.watch` on the inbox, commands and transcripts directories (`watchedSleep`, watchers kept across sleeps so nothing lands unnoticed). A failed turn is published in the status (`error`) and logged to the window; the loop goes on. It ends on a `stop` request, when the project directory is gone, or (`exitWhenIdle`, the compiled probe) once nothing is pending. Everything durable is on disk: turns, locks, receipts, status; a daemon's memory holds only its session caches. The orchestrator window shows streamed text and tool lines like a worker's (`windowHooks`), and the same events go to the turn's live file (`DaemonOptions.live`, begun before the status says `turn`, removed after `session.turn()` resolves and before it says `idle`)
- `src/core/agent-loop/orc/live.ts` — the turn's live side channel, `projects/<id>/orchestrator/live.jsonl`: one file per project (one daemon, one turn at a time; no per-turn directory to prune after crashes), replaced at turn start by its `{seq: 0, kind: "start", run, turn}` header and removed at turn end once the turn's entries are durable, so a late client never sees live data for a finished turn. `liveWriter` appends `{seq, head, kind: text|status|tool_start|tool_end|truncated, …}` events (`head` is the daemon's transcript head when the event happened; `status` is a plain line such as a memory-index warning) on a promise chain the turn never awaits: appends cannot block or fail a turn, the first I/O error is logged once to the window and later ones are silent; `end()` waits at most `LIVE_END_WAIT_MS` (2s) for the chain, then removes the file anyway (a straggling append may recreate a headerless file, which no reader consumes and the next `begin` replaces). `LIVE_CAP_BYTES` (1 MiB of UTF-8) per turn: text past it becomes a single `truncated` event, tool events are still appended (the transcript bounds them). `liveReader` tails by byte offset, complete lines only (bytes are split at newlines before decoding, so a multibyte character cut by a read is whole), consuming nothing until the header names the expected run and turn (`status.json`'s `run` and `turns`); it re-reads the header line on every read and starts over when it changed (a replaced or rewritten file, whatever its size) or names another turn; a re-read seq is skipped and a gap in seq is reported once. The transcript stays the durable record, written only at message boundaries; the live file is presentation
- `src/core/agent-loop/orc/channel.ts` — the file protocol under `.runtime/projects/<id>/orchestrator/` (its message types are `src/protocol/daemon.ts`): `status.json` (pid, run, `idle|turn|stopped`, since, turn count, the last turn's context estimate and error; atomic rename; its `run` and `turns` key the live file), `commands/<ts>-<seq>-<id>.json` requests (`request`/`takeRequests`, oldest first, a request is read once and never retried: a daemon crash mid-request leaves the client's wait to time out), `acks/<id>.json` answers (`acknowledge`/`awaitAck`, collected and removed by the waiting client, else pruned after an hour on the next start; `awaitAck` fails fast when the daemon is dead and after `ACK_TIMEOUT_MS` (15s) otherwise). Liveness is `daemonPid` (the daemon lock's `owner.json` pid, `pidAlive`); a status file whose pid is not that process is stale and never counts as busy. Cancellation reuses `transcript/orchestrator.jsonl.cancel` from `cancelSession` (which now returns the token) rather than a request
- `src/core/agent-loop/orc/client.ts` — the TUI's side. `ensureDaemon` starts one through the runner when none is alive (a `LaunchFailed` for a start that lost the lock race still counts as running); `daemonKeeper` is `AppDeps.ensureDaemon`: called when a page opens (in the background, never blocking the page) and on every poll, restarting a dead daemon at most once per `RESTART_BACKOFF_MS` (15s) and returning the line to show; the CLI aborts a launch still being confirmed when the TUI quits. `stopDaemon` sends `stop`, waits `STOP_WAIT_MS` (10s) for the recorded pid, then kills the `orchestrator` window and waits 3s more, else throws. `createClientOrchestrator` is the `Orchestrator` every page gets in production: `say` publishes to the inbox exactly as before; `pending()` is "the live daemon is in a turn"; `turn()` follows that turn from disk (`status.json` every `FOLLOW_MS` (250ms), re-reading the transcript and calling `onRefresh` → `App.syncTranscript` whenever the head moves, one last time when the turn ends; between looks, while the status says `turn`, it tails `live.jsonl` every `LIVE_MS` (125ms: twice per look, `tailLive`) and feeds the events through the same hooks the in-process turn used (`ClientDeps.write`/`onTool`/`onToolResult` → `App.stream`/`toolStarted`/`calls.finish`; `status` lines and the `truncated` marker go to `notice`, so they persist as page notices across the re-renders a turn's entries cause, where the in-process turn's plain lines lasted only until the next re-render): an event tagged with the head the view shows is ahead of the record and is shown; one tagged with another head is behind a durable entry — the first such event in a batch re-syncs the transcript once, and whatever is still not at the head is dropped as superseded. So a durable entry replaces the live rendering of what it records (`syncTranscript` drops the stream's partial text and running calls with the old rendering; while the page is busy it also leaves the newest assistant entry's calls without a result out of the record's rendering, `restore(…, unresolvedCalls(entries))`, since the live `tool_start` shows them running — `openPage` does the same when `pending()` says a turn is running, and `runTurn`'s finally re-syncs once when such calls were left out, so a call the record never resolves gets its "interrupted" marker from the record), nothing renders twice, and a TUI opened mid-turn restores the transcript, replays the file from its start (only the events ahead of the head show) and tails on; a turn that began and ended between looks still counts via the turn counter; after this client's own send it waits `START_GRACE_MS` (5s) for the daemon to pick the input up; a failed turn's error becomes a page notice); `cancel` writes the cancel request and reports the acknowledgement (or its absence) through `ToolEvents.notice`; `compact`, `clear` (client-side disk checks first, the daemon rechecks under its locks) and `observeModel` (after `/model` saved, the daemon confirms which model its next request uses) are requests awaited for their ack; `contextUsage`/`contextWindow` come from the status. Nothing here calls a model or appends to the orchestrator's transcript: only the daemon mutates it, any number of TUIs read and enqueue
- `src/providers/` — `Provider` interface over an Anthropic-shaped transcript; `anthropic.ts` (SDK) and `openai.ts` (Codex subscription Responses, translated; preserves encrypted reasoning and tool IDs). `providerFor(model)`: `claude*` → anthropic, else openai. Both `complete` paths run under `retry.ts` (`withTransientRetries`; the Codex SDK with `maxRetries: 0`, the Anthropic SDK with `maxRetries: 0`; bounded recovery owns retry policy and avoids hidden duplicate attempts): a transport error or a 408/409/429/5xx/529 on the initial request is retried up to three times (≈1s/4s/10s, jittered), each retry announced through `CompleteRequest.onNotice` (the loop shows it as a plain status line); a stream that has delivered an event is never retried, and a cancel stops at once with its reason
- `src/login/accounts.ts` (and `src/providers/account.ts` for the Provider of the active account) — subscription accounts only: config `account` selects a Claude profile, `openaiAccount` selects a Codex profile; empty means `default`. API keys, old saved keys, developer-platform profiles and billing fallbacks are unsupported.
- `src/login/claude.ts` / `src/login/codex.ts` — provider-specific OAuth login, import and refresh. `src/login/oauth.ts` shares PKCE callbacks, private atomic writes and cross-process locks. A run is closed by an exclusive create of `runs/<id>.<run>.exit`, by whoever sends its notice (or silently, when it ended on a report), so each run gets at most one notice; claims are pruned only after a day, so an old run's follow-up still sees its claim after a quick respawn. The watchdog skips a check when tmux could not be asked and only sends once the run's pid is dead (`process.kill(pid, 0)`). - `src/core/tmux/merges.ts` — merged PRs. `mergeWatcher({ gh?, repo?, pr?, live, kill?, alive?, dirty?, now?, everyMs?, waitMs? })` returns `check(project)`, which the orchestrator daemon runs on its poll (`checkProject`: at most every `MERGE_POLL_MS` (30s) per project, one check per project at a time). Orchestrator process model: the TUI never runs an orchestrator turn. Each project's turns run in its daemon (`src/core/agent-loop/orc/daemon.ts`, the `orchestrator` tmux window), which owns the two turn locks while a turn runs and keeps going when every TUI is closed; closing the TUI mid-turn loses nothing (the next open restores the transcript, and a still-running turn shows busy again). Pages following a daemon turn show it as an in-process turn showed: the streamed text, each tool starting and ending, "thinking…"/"working…", fed from the daemon's live file (`src/core/agent-loop/orc/live.ts`), with completed entries replacing that rendering as they land; every attached TUI sees it, and one opened mid-turn resumes the view without loss or duplication. A crashed daemon leaves a stale lock/status with a dead pid, an `[agent-exit] orchestrator …` notice in its own inbox (read by the next daemon) and the TUI's keeper restarts it on the next poll. `orca pull` users must stop the orchestrator daemons too (`orca stop <project>`, or delete the project), since running daemons keep the old code. Launch identity: the daemon publishes `transcript/orchestrator.jsonl.launch` with its own run once it holds the daemon lock and re-asserts it on every loop pass (`assertLaunch`), so a concurrent start that lost the lock race and published last cannot leave cancels pointing at a run nobody runs. Turn-lock gates (`turnLocksHeld`: `session.pending()`, clear checks) ignore a lock whose owner pid is dead (`lockHeld`), so a daemon killed mid-turn by a signal (its `finally` never runs) cannot block its successor: `ownTurn` moves the dead lock aside. During a turn the daemon's 100ms poll also answers `compact` (sets the flag the turn reads at its next safe boundary) and `model` (confirms whatever is saved) requests; `clear` and `stop` wait for the turn to end. `awaitAck` fails fast when the daemon dies or is replaced by a new run while waiting.

Session refresh/queues: `/refresh`, prompt submission (including busy/login-held input), and passive polling reconcile shared local state without calling `say`, `turn`, tools, watchdogs, or restarts. Submission starts before refresh and never awaits it; local active context reload waits until idle. `onRefresh` restores shared history before local streaming. `Transcript.refresh/consumed`, `inbox.consume`, and `storage-lock.ts` implement locked snapshot/publication and exact committed input/delivery receipts; no text matching or disappearance-based acknowledgements. Orchestrator daemons own two cross-process turn locks (the checkout turn lock, then the conversation's own `turn-locks/<id>`), refresh before a turn, and require fresh consumed input rather than replaying history after cleanup or errors. Clear/delete also honor turn ownership (delete only the conversation's own lock, so a sibling mid-turn on the shared checkout does not block it; refusals name the holder). No time-based stale-lock stealing, only race-safe takeover of a verifiably dead owner PID; mixed old/new processes cannot provide these guarantees. See docs/SESSION_REFRESH.md (including branch reviewer constraints).

- Public home: `prompts/`, `tools/`, `skills/`, `projects/`, `memory.sqlite`, `.runtime/`. Project artifacts: `tasks.json`, rebuildable `cache/`, `transcript/`, `tool-outputs/` (worker `reports/` included), `images/`. Configuration, credentials, pending events, supervised command output and recovery state are under `.runtime/`, which is durable. See `docs/ORCA_HOME.md`.
- Fresh homes only: older layout versions fail before normal startup. `scripts/migrate-layout.ts` is the historical v1→v2 utility, not an upgrade to v3. Never silently reset or reinterpret old state.
- Import transcript pairing from `data/transcripts/` and database/ledger helpers from `data/sqlite/`; obsolete `data/memory/` forwarding modules are removed. TUI integration test helpers live in `src/test/app-fixture.ts`.
