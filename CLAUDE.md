# orca

A light-context agent harness with one adaptive tool loop and focused workers. Delegation, review and publication are independent capabilities. One tmux session per project contains agent windows; persistent state and process supervision supply continuity. See docs/ADAPTIVE_RUNTIME.md for current behavior.

Bun + TypeScript. Use `bun` for everything (`bun test`, `bun run check`, `bun src/cli/main.ts`). No Node, npm or vite.

`install.sh` bootstraps the dedicated `~/.orca/.runtime/app` checkout and delegates the build/atomic binary install to `src/cli/scripts/install.ts`. It preserves runtime state, refuses existing app paths, and adds PATH for supported shells unless `--no-modify-path` is passed. Bootstrap tests use temporary homes and fake downloads/builds; never run installation against the real home for validation.

Layout:

The tree has the codex-rs shape, bottom first: config → login → providers → protocol → core → exec · tui → cli. Every import points down, between packages and inside them; `src/organization.test.ts` is the check (read its header), CLAUDE.md is the prose. The orders it enforces:

- packages: `config` < `login` < `providers` < `protocol` < `core` < `exec` · `tui` < `cli` (`exec` and `tui` never import each other; type-only imports count)
- `providers/`: images · sanitize · retry < catalog/ < search/ < provider < anthropic · openai < account
- `core/`: proc · execution < data/ < definitions/ < install/ · tmux/ · prompt/ < tools/ < agent-loop/; `core/data/`: storage-lock · sqlite/ < projects/ < run-ownership/ · images/ < inbox/ < processes/ · knowledge/ · tasks/ · transcripts/ < memory/; `core/tools/`: registry < the tools (one file or sub-folder each) < mount; `core/agent-loop/`: loop/ < orc/
- `tui/`: commands/ · history · components/ < header/ · conversation/ < footer/ < screen/ < app-state < work-page < app
- files directly inside one folder are one unit (no order between them); a type a lower file needs from above is narrowed in place, e.g. `ContextDeps` in `compaction.ts` for `AgentDeps`, `ConsumeTarget` in `inbox.ts` for `Transcript`

Barrels: every folder that is imported from outside has an `index.ts` holding nothing but named re-exports of the files directly in it (`export { a, type B } from "./file"`; `export * as ns from "./file"` for a namespace; never a sub-folder, a parent, another barrel or `export *`), dependencies first. Non-test code crossing a folder boundary imports that folder's barrel (`../../core/data/tasks`), never a deep module, and adds missing names to the barrel. Two exceptions, both inside one package: imports inside a folder stay direct, and a file of an ancestor folder is imported directly too (`../sanitize`, `../../proc`, `../storage-lock`) — never the ancestor's barrel (`..`, `../..`), which would reach back into the importing folder and make a cycle; (b) still orders these. Tests (`*.test.ts`, `src/test/`) are exempt from the order and barrel rules (a)–(c) and may import anything. `core/tools/index.ts` is the barrel; `core/tools/mount.ts` is the registry mount.

Size gates (the same test): a non-test file ≤ 800 lines, a test file ≤ 1500, a function ≤ 8 parameters, a barrel ≤ 40 exports. Today's offenders are listed in the test's `DEBT` table with their current numbers as ceilings: growth fails; shrink the ceiling when the file shrinks (the test does not force it); a row within the gate must be deleted. `src/` holds only the package folders, `test/` and that test — no loose files.

- `src/core/agent-loop/orc/daemon.ts` — the orchestrator as a long-lived process (`runDaemon`, the poll loop; its process entry `orchestratorAgent` is `src/exec/daemon.ts`): `orca agent --role orchestrator --project p` (what the TUI launches through `local.start`, in the `orchestrator` window of `orca-<project>`, under the same `sh -c` wrapper and `confirmLaunch` as workers) takes the project's `daemon-locks/<project>` for its lifetime (a second daemon exits 70 before writing a run record, so its launch fails and the first keeps running), runs under `supervise` (run record `runs/orchestrator.json`, crash/signal notices to its own inbox for the next daemon; a clean stop claims its run first, so no notice), and loops: answer queued requests (`clear`, `compact`, `model`, `stop`), take a cancel request for its launch (`takeCancellation`: `session.cancel()`, acknowledged under the cancel token), start the exit watchdog and merge watcher every `WATCH_MS` (2s) in the background (one pass at a time, awaited only before an idle exit or a stop, so input never waits behind the merge watcher's `gh` calls), then `session.pending()` → `session.turn()` (status `turn`, a 100ms cancel poll meanwhile) or sleep `DAEMON_POLL_MS` (1s) — woken early by `fs.watch` on the inbox, commands and transcripts directories (`watchedSleep`, watchers kept across sleeps so nothing lands unnoticed). A failed turn is published in the status (`error`) and logged to the window; the loop goes on. It ends on a `stop` request, when the project directory is gone, or (`exitWhenIdle`, the compiled probe) once nothing is pending. Everything durable is on disk: turns, locks, receipts, status; a daemon's memory holds only its session caches. The orchestrator window shows streamed text and tool lines like a worker's (`windowHooks`), and the same events go to the turn's live file (`DaemonOptions.live`, begun before the status says `turn`, removed after `session.turn()` resolves and before it says `idle`)
- `src/core/agent-loop/orc/live.ts` — the turn's live side channel, `projects/<id>/orchestrator/live.jsonl`: one file per project (one daemon, one turn at a time; no per-turn directory to prune after crashes), replaced at turn start by its `{seq: 0, kind: "start", run, turn}` header and removed at turn end once the turn's entries are durable, so a late client never sees live data for a finished turn. `liveWriter` appends `{seq, head, kind: text|status|tool_start|tool_end|truncated, …}` events (`head` is the daemon's transcript head when the event happened; `status` is a plain line such as a memory-index warning) on a promise chain the turn never awaits: appends cannot block or fail a turn, the first I/O error is logged once to the window and later ones are silent; `end()` waits at most `LIVE_END_WAIT_MS` (2s) for the chain, then removes the file anyway (a straggling append may recreate a headerless file, which no reader consumes and the next `begin` replaces). `LIVE_CAP_BYTES` (1 MiB of UTF-8) per turn: text past it becomes a single `truncated` event, tool events are still appended (the transcript bounds them). `liveReader` tails by byte offset, complete lines only (bytes are split at newlines before decoding, so a multibyte character cut by a read is whole), consuming nothing until the header names the expected run and turn (`status.json`'s `run` and `turns`); it re-reads the header line on every read and starts over when it changed (a replaced or rewritten file, whatever its size) or names another turn; a re-read seq is skipped and a gap in seq is reported once. The transcript stays the durable record, written only at message boundaries; the live file is presentation
- `src/core/agent-loop/orc/channel.ts` — the file protocol under `.runtime/projects/<id>/orchestrator/` (its message types are `src/protocol/daemon.ts`): `status.json` (pid, run, `idle|turn|stopped`, since, turn count, the last turn's context estimate and error; atomic rename; its `run` and `turns` key the live file), `commands/<ts>-<seq>-<id>.json` requests (`request`/`takeRequests`, oldest first, a request is read once and never retried: a daemon crash mid-request leaves the client's wait to time out), `acks/<id>.json` answers (`acknowledge`/`awaitAck`, collected and removed by the waiting client, else pruned after an hour on the next start; `awaitAck` fails fast when the daemon is dead and after `ACK_TIMEOUT_MS` (15s) otherwise). Liveness is `daemonPid` (the daemon lock's `owner.json` pid, `pidAlive`); a status file whose pid is not that process is stale and never counts as busy. Cancellation reuses `transcript/orchestrator.jsonl.cancel` from `cancelSession` (which now returns the token) rather than a request

- `src/core/tmux/exits.ts` — `[agent-exit]` notices to the orchestrator's inbox, from the agent's id, when a worker or reviewer stops without reporting — or the orchestrator daemon itself crashes or is signal-killed (a self-notice the next daemon reads first; a clean `orca stop`/deletion claims the run and sends none). A successful `message` to "orchestrator" sets state `reported`; any later tool call or inbox message sets it back to `running`, so an interim "starting…" message does not silence a later notice. A run is closed by an exclusive create of `runs/<id>.<run>.exit`, by whoever sends its notice (or silently, when it ended on a report), so each run gets at most one notice; claims are pruned only after a day, so an old run's follow-up still sees its claim after a quick respawn. The watchdog skips a check when tmux could not be asked and only sends once the run's pid is dead (`process.kill(pid, 0)`). Notices carry role, branch, last step and tool, the error, and the uncommitted count, computed only when a notice is built: `git --no-optional-locks status --porcelain` with a 3s hard timeout (1s in a signal handler), "unknown" on timeout; the watchdog runs it in `worktrees/<slug(branch)>`
- `src/core/tmux/merges.ts` — read-only PR observation. `mergeWatcher({ repo?, pr?, now?, everyMs? })` checks linked task PRs at most every 30s, coalesces lookups, archives verified merges and uses the durable observation outbox for one notification. Compaction: see docs/COMPACTION.md. The orchestrator's background (rolling) compaction starts at 25% of the selected model's window and keeps ~50k tokens verbatim, the tail target falling back to half the effective trigger when it would otherwise reach or exceed that trigger (newest exchange always stays whole) (`DEFAULT_TRIGGER_FRACTION`/`DEFAULT_TAIL_TOKENS` in `rolling-memory.ts`, from the experiment report on branch experiment-rolling-compaction; `RollingOptions.triggerTokens`/`tailTokens` override). `/compact` and auto compaction resolve foreground model/provider/settings once per safe boundary; orchestrator memory reuses the resolved foreground account/model and splits summary requests to fit that model. Each part has its own deadline; changing account/model/window cancels stale background work and resets backoff. Model context uses `Transcript.chain()`; UI replay uses `Transcript.history()` via orchestrator `entries()`. Summaries are best-effort/lossy. Orchestrators use background rolling memory (three parts in order: Tasks from the ledger and Preferences from saved `facts`, both as saved, then the model's `{summary, pending}` of the rest; `rolling-memory.ts` `memoryText`/`preferenceLines`, `rolling-summary.ts`; legacy `{user, project, pending, tasks}` memory seeds the next summary via `previousMemory`) and scoped SQLite search/read via task; workers/reviewers pin their complete original task. The searchable archive in `memory.sqlite` (`core/data/memory/archive.ts`: `entries`, `entry_search`, `tasks`, `entry_tasks`, `sources`) is written only where context is replaced: rolling compaction (`archiveTranscript` before the summary job and again before publishing it) and `/clear-context` (`archiveBestEffort`, since cleared messages leave the context too); never at turn end or by a tool. `task search_history/read_history` and `history` only read it, so messages since the last compaction are found in live context, not by search. The task ledger (`task_ledger_*`) still saves on every task change. Both preserve original disk/UI entries and exact receipts. Transcript records are appended in place (`transcript-storage.ts` `publish`: open for append, one probed byte for the separator, write, fsync; cost is the record, never the file, and the inode stays): a record is committed once written, fsynced and let stand by the signal and `authorize`; any earlier failure truncates the file back to its prior length, a torn final line is skipped by every reader and the next append starts a fresh line; close and (for a new file) directory-sync failures after the commit are warnings. `Transcript.append` reloads only when the file's version changed.

Context clearing: `/clear-context` resets the project to how it was when created. Confirming runs `resetProject` (`tui/commands/project.ts`, `AppDeps.resetProject` in tests): the ownership cascade's `deleteProject` (history, tasks and their ledger rows via `purgeLedgerProject`, questions, images, agents, worktrees, the project's state rows), then `ensureProject` with the same id in the same folder, then its own `name` and inherited settings keys and its pin written back; `App.confirmClear` closes the page in `beforeRemove` (which now runs before anything is removed, so a throw there cancels cleanly) and reopens it in the same tab with the draft. Nothing of the old conversation stays on disk; branches, saved facts and the folder do. The question's title carries `describeDeletion` (tasks, agents, questions, images, worktrees, uncommitted count), and uncommitted worktree files are discarded only when it could be shown. Refused like a deletion (live or unknown agents, a running command, the turn lock) and like the old clear (below). `Orchestrator.clear`, the daemon's `clear` request and the `context-boundary` writer are no longer reached from the TUI; boundaries in existing transcripts are still read. The rest of this paragraph describes the confirmation and those boundaries. It is a local Cancel-default footer confirmation, never a user/model message or provider request. Refuse in agent views, while running/compacting, or with any raw durable/paused inbox or TUI held/persisting input; recheck on confirmation. Captured Page/directory identity and the project-state lock protect ownership. Page/menu changes, Escape/Ctrl+C and resize invalidate confirmation without touching drafts. Input recall excludes `/clear-context`. `Orchestrator.checkClear()` / `clear(signal?)` append an explicit `context-boundary` with intact parent links using transcript publication (in production the client checks from disk, sends a `clear` request and the daemon runs the same `clear` under its locks, refusing in the ack when input landed meanwhile); chain/branch stop before it; saved history retains originals, while UI/exit replay show only entries after it. Clear also evicts rebuildable project cache and resets rendered rows, scroll, selection and local notices. Routine model-request lifecycle metadata stays in durable diagnostics and is never shown above the composer, including events from older daemons. Actual API failures, retry errors and exhausted-quota feedback remain visible. Other runtime notices, errors and command feedback live only in the temporary row above the composer; the next input key clears it, even before its frame paints. Transcript restoration never emits status feedback. Worker attachment suppresses metadata already present on disk; daemon clients skip status events present at attachment while still restoring streamed replies and tools. Only newly observed live events can show another note; no notification history is persisted. Compaction's original-task pin and retrieval warning are scoped after the latest boundary, never resurrecting pre-clear context. Orchestrator inbox publication now shares the project lock with clear; later external sends remain new input. No inbox draining, retries, resume or worker restarts. See docs/COMPACTION.md for commit/cancellation semantics and the cooperative cross-process locking and mixed-version limitations in docs/SESSION_REFRESH.md.

Orchestrator process model: the TUI never runs an orchestrator turn. Each project's turns run in its daemon (`src/core/agent-loop/orc/daemon.ts`, the `orchestrator` tmux window), which owns the two turn locks while a turn runs and keeps going when every TUI is closed; closing the TUI mid-turn loses nothing (the next open restores the transcript, and a still-running turn shows busy again). Pages following a daemon turn show it as an in-process turn showed: the streamed text, each tool starting and ending, "thinking…"/"working…", fed from the daemon's live file (`src/core/agent-loop/orc/live.ts`), with completed entries replacing that rendering as they land; every attached TUI sees it, and one opened mid-turn resumes the view without loss or duplication. A crashed daemon leaves a stale lock/status with a dead pid, an `[agent-exit] orchestrator …` notice in its own inbox (read by the next daemon) and the TUI's keeper restarts it on the next poll. `orca pull` installs globally, then invokes the new binary to schedule a detached reload helper (`exec/update.ts`, `orc/reload.ts`). Stop requests wait between turns; the helper never force-kills workers or daemons. Per-project update intents survive a failed handoff; `orca reload` retries them. Helpers serialize and verify the installed build, and new clients refuse a differently built daemon. Reopen existing TUIs; workers/reviewers finish on their loaded builds. Older updaters need one explicit `orca reload` after first installing this version. Launch identity: the daemon publishes `transcript/orchestrator.jsonl.launch` with its own run once it holds the daemon lock and re-asserts it on every loop pass (`assertLaunch`), so a concurrent start that lost the lock race and published last cannot leave cancels pointing at a run nobody runs. Turn-lock gates (`turnLocksHeld`: `session.pending()`, clear checks) ignore a lock whose owner pid is dead (`lockHeld`), so a daemon killed mid-turn by a signal (its `finally` never runs) cannot block its successor: `ownTurn` moves the dead lock aside. During a turn the daemon's 100ms poll also answers `compact` (sets the flag the turn reads at its next safe boundary) and `model` (confirms whatever is saved) requests; `clear` and `stop` wait for the turn to end. `awaitAck` fails fast when the daemon dies or is replaced by a new run while waiting.

Session refresh/queues: prompt submission (including busy/login-held input), and passive polling reconcile shared local state without calling `say`, `turn`, tools, watchdogs, or restarts. Submission starts before refresh and never awaits it; local active context reload waits until idle. `onRefresh` restores shared history before local streaming. `Transcript.refresh/consumed`, `inbox.consume`, and `storage-lock.ts` implement locked snapshot/publication and exact committed input/delivery receipts; no text matching or disappearance-based acknowledgements. Orchestrator daemons own the cross-process conversation lock (`turn-locks/<id>`), refresh before a turn, and require fresh consumed input rather than replaying history after cleanup or errors. Clear/delete also honor turn ownership (delete only the conversation's own lock, so a sibling mid-turn on the shared checkout does not block it; refusals name the holder). No time-based stale-lock stealing, only race-safe takeover of a verifiably dead owner PID; mixed old/new processes cannot provide these guarantees. See docs/SESSION_REFRESH.md (including branch reviewer constraints).

Home layout 3 and source organization:

Per-run epochs fence inbox commits, tools and launches, so rapid resume cannot revive old work or consume the new instruction. Daemon keepers/update handoffs skip stopped projects. Project scope includes its directory identity so recreated names cannot inherit prior bindings/settings/decisions.
- Public home: `prompts/`, `tools/`, `skills/`, `projects/`, `memory.sqlite`, `.runtime/`. Project artifacts: `tasks.json`, rebuildable `cache/`, `transcript/`, `tool-outputs/` (worker `reports/` included), `images/`. Directory projects: `config/directory-projects.ts` owns the UUID catalog and defaults; `config/conversation-identity.ts` owns portable per-conversation `.identity.json`. `core/data/projects/catalog.ts` (namespace export `directories`) separates directory projects from legacy storage/conversation IDs. Ownership tree and deletion: `src/core/tmux/ownership.ts` is the one place that reads and deletes along the whole chain, home → folder (a directory project) → project (a conversation) → session (the folder itself or a worker worktree) → items (agents, tasks, questions, images, commands, sandboxes, outputs, caches); its header says where each level is recorded. `projectNode`/`folderNode` read it (worktrees from disk through `paths.worktreeRoots`, items from the session registry); `deleteProject` cascades down (every worktree removed with `git worktree remove --force`, `workspaces.release` for the item and session records, `directories.detach` for the folder membership, then the project's files, search archive and pin) and `deleteFolder` deletes each project after checking all of them, then the folder record (`directories.removeFolder`). Nothing above or beside the node is touched: the folder's directory, the repository and its branches stay, as do sibling conversations' worktrees. Still refused while agents are live or unknown, a command may be running, the turn lock is held, or a worktree-folder entry cannot be verified; worktrees with uncommitted files refuse unless `discard` is set, which the Projects page sets only after its y/n question has shown the count (`describeDeletion`). `tui/commands/project.ts` only supplies `stopDaemon`. On the Projects page `d` on a folder row deletes the folder, on a conversation row that conversation.

MCP servers: see docs/MCP.md. The user manages them in one hand-edited file, `~/.orca/mcp.json` (`paths.mcp`), in the `mcpServers` shape other clients use: a name and either `command`/`args`/`env` (a local program) or `url`/`headers` (Streamable HTTP), plus `disabled` and `timeout` (seconds); `${NAME}` is taken from the environment. `src/core/mcp/` (a core folder below `tools`): `config.ts` reads and validates the file on every use (`readServers`: one bad entry is that entry's `problem`, never the others'; `usableServer` throws what the user should read), `client.ts` holds the per-process connections (`withServer`: opened on first use, kept `IDLE_MS` = 10 minutes, replaced when the entry changes, closed when the connection fails but not when the server merely refuses a request or the request was wrong (`UsageError`); a failed start includes the server's stderr; nothing is retried), `auth.ts` the OAuth sign-in (`.runtime/mcp-auth/`, keyed by name and url). Agents reach servers through the one static `mcp` tool (`core/tools/mcp.ts`: servers, tools, schema, call, resources, prompts), so server schemas never enter the prompt and the tool list stays cache-stable; all three roles have it. `orca mcp [test|login|logout]` (`src/cli/scripts/mcp.ts`) lists, tries and signs in; nothing writes the file except creating an empty one. There is no slash command, no SQLite definition and no per-project file. Tests use fixture servers and a temporary home, never a real server or the user's file.

Workspace session cleanup: see docs/WORKSPACE_CLEANUP.md. Finished work gives its checkout back without waiting for the 14 days: the daemon's maintenance pass (`removeFinishedWorktrees` in `tmux/workspace-cleanup.ts`, every 5 minutes, `FINISHED_GRACE_MS` 10 minutes after the last activity) runs `git worktree remove` on a worker worktree whose tasks are all merged, closed or removed, or (no PR to observe) whose branch has moved since creation and is contained in the default branch. It removes only the checkout: branch, commits, transcripts and task records stay, and a session whose tasks are settled is archived at once so `orca clean` may purge its records. Live or queued agents, open processes, source edits, untracked or unrecognised ignored files keep it; it holds the branch's spawn lock, and never stops or starts an agent. `projects/workspace-sessions.ts` owns path lookup, stable directory identity, resource references and 14-day archive state in existing SQLite metadata. `tmux/workspace-*` discovers legacy resources, checks liveness, and implements explicit cleanup; the daemon maintenance pass only archives. `orca clean --preview` previews against an in-memory overlay; `orca clean` removes eligible archived sessions. Saved tool outputs no session owns (`core/tools/bash/output.ts` `pruneOutputs`: `<uuid>.txt|partial|running` at any depth by seven days and the 256 MiB budget, any other unowned file by seven days alone, stale `.running` included; a top-level entry registered as an artifact keeps everything under it, `verification/` is its sandbox's) are pruned for every project by `orca clean` (listed, not deleted, in preview) and once per orchestrator daemon in its first maintenance pass, best effort. Preserve running/queued work, source edits, ordinary directories, referenced images/tasks and shared resources. Sandbox scratch still closes promptly, while workspace-owned evidence follows archive/clean retention. Test deletion only in isolated homes and checkouts; never validate against a user's running sessions or real caches.
